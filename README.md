# Docs AI Agent

ИИ-агент-помощник, который читает и ищет информацию в тысячах файлов API-справки
и пишет рабочий код по найденной документации.

Состоит из фронтенда (React + TypeScript + Tailwind CSS) и бэкенда (Python 3.14 + pydantic-ai + FastAPI + SQLite),
запускается в Docker-контейнерах.

## Архитектура

```
[frontend nginx :8080] --proxy /api, /docs, /redoc, /openapi.json--> [backend uvicorn :8000]
                                          tools: ripgrep / read_file / file_info / list_dir
                                          agents: researcher -> DOCs/CAD specialists -> critic -> writer
                                          sqlite: чаты и история переписки
         ./docs (RO-маунт) ----------------------^
         API samples (RO-маунт) ----------------^
```

### Агентский цикл с критикой результата поиска

Каждое сообщение пользователя запускает пайплайн из трёх агентов:

1. **Researcher** — сначала определяет, относится ли вопрос к T-FLEX CAD или T-FLEX DOCs,
   затем ищет только в соответствующем подкаталоге корпуса инструментами (`search_docs`
   на ripgrep, `read_file`, `file_info`, `list_dir`) и выдаёт черновик фактов со ссылками
   `файл:строка`. Для предметного исследования он может делегировать задачу профильному
   субагенту T-FLEX DOCs (импорт, тестовые данные, единицы измерения, плагины/UI) или
   одному из CAD-субагентов (документ, 2D, 3D); результат
   возвращается исследователю для проверки.
   Для T-FLEX DOCs исследователь выбирает направление по сценарию
   (объекты, параметры, связи, жизненный цикл, UI и т. п.) и проверяет точные сигнатуры
   и порядок изменения объектов. Последующий ход идёт с накопленной историей.
2. **Critic** — структурированно оценивает, достаточно ли собранного для написания
   **рабочего** кода (подтверждённые сигнатуры, полнота сценария работы с API).
   Если нет — перечисляет конкретные пробелы и предлагает уточняющие ripgrep-запросы,
   и Researcher продолжает цикл (до `MAX_CRITIC_ROUNDS` итераций).
3. **Writer** — пишет финальный ответ с кодом C# по подтверждённым фактам и списком
   источников. Только подтверждённое документацией может попасть в код.

Все фазы идут во фронтенд по SSE (`phase`, `tool`, `draft`, `critique`, `text`) —
см. «Фоновая обработка» ниже.

### Фоновая обработка

Обработка сообщения идёт фоновой задачей на сервере и не зависит от вкладки:
`POST /api/chats/{id}/messages` сразу отвечает `202 {run_id, chat}`, а события
читаются отдельным SSE-потоком `GET /api/chats/{id}/runs/{run_id}/events?from=N` —
сначала накопленные с номера N, потом новые вживую.

- Перезагрузка страницы и закрытие вкладки не прерывают обработку: вернувшись,
  пользователь видит тот же чат (`/chat/{id}`) с накопленным ходом работы и
  продолжением вживую; чат с идущим запуском помечен точкой в списке.
- Кнопка «Остановить» (вместо отправки, пока агент работает) прекращает запуск;
  под вопросом появляется пометка «Ответ не получен — отправьте сообщение ещё раз.».
- При ошибке провайдера в чат сохраняются уже показанный текст и краткая ошибка,
  полный дамп уходит в лог LLM.
- Перезапуск сервера теряет идущие запуски (ответ не сохраняется) — у вопроса
  остаётся та же пометка. Настройки развёртывания от этого не меняются.
- События завершённого запуска хранятся в памяти ещё 60 секунд — на случай
  обрыва связи в момент завершения.

### Администрирование агента

Страница `/admin` позволяет редактировать промпты исследователя, делегирования,
критика и писателя, создавать/редактировать/удалять Markdown-навыки и управлять
субагентами. Изменения сохраняются в томе `/app/data` и применяются к новым
запросам без перезапуска; уже выполняющиеся запросы продолжают работу с прежней
конфигурацией.

Для входа задайте в `.env` уникальный `ADMIN_PASSWORD` длиной не менее 16 символов
и перезапустите backend. При незаданном или коротком пароле административный API
отключён. После входа используется HttpOnly cookie с ограниченным сроком действия;
изменяющие запросы дополнительно требуют same-origin заголовок.

### Инструменты агента

| Инструмент    | Что делает                                                                                                        |
|---------------|-------------------------------------------------------------------------------------------------------------------|
| `search_doc_topics` | Ищет GUID- и человекочитаемые страницы по иерархии `index.md` и возвращает доменный путь в оглавлении |
| `search_indexed_pages` | Ищет по полным текстам страниц, прямо указанных в `index.md`, с метаданными, ключевыми словами и выдержками с номерами строк |
| `search_api_examples` / `read_api_example` | Ищет и читает ограниченные фрагменты исходников примеров T-FLEX DOCs API; результат нужно сверять с документацией |
| `search_docs` | Поиск кандидатов через **ripgrep** (regex или literal), затем ранжирование документов BM25 по исходному вопросу; `glob` ограничивает продукт |
| `read_file`   | Полное чтение файла (при переполнении бюджета контекста — порцией с подсказкой продолжения через `start_line`)      |
| `file_info`   | Оценка объёма файла: байты, строки, примерные токены, доля от окна контекста — чтобы не вылезти за контекст         |
| `list_dir`    | Листинг каталогов документации                                                                                     |

Навыки и субагенты для импорта в справочники, генерации объектов и связей,
преобразования единиц и расширения UI основаны на примерах
`Graphs`, `ImportReference`, `ReferenceObjectsGenerator` и `UnitConverter`.
Примеры подключаются к backend только для чтения. Задайте `DOCS_API_EXAMPLES_PATH` в `.env`
как путь к каталогу «Примеры использования API» установленного T-FLEX DOCs; шаблон
`.env.example` содержит стандартный путь установки T-FLEX DOCs 17. Если папка не
подключена, исследование продолжается только по документации. Примеры помогают
найти работающие сценарии, но не заменяют подтверждение API по справке.

Проверить `search_indexed_pages` без вызова модели можно через
`POST /api/tools/search-indexed-pages` (доступен также в Swagger UI `/docs`):

```json
{
  "query": "ServerConnection",
  "product": "TFlexDOCs API",
  "limit": 5
}
```

Ответ содержит число индексированных страниц, длительность поиска, найденные пути,
ключевые слова, разделы, выдержки и номера строк.

`search_doc_topics` использует иерархию ссылок из `index.md`, включая таблицу
пространств имён и таблицы типов на связанных страницах: сначала помогает выбрать
домен и страницу, затем `search_docs` и `read_file` подтверждают API по содержимому.
Это даёт будущим доменным навыкам и субагентам общий каталог вместо ручной привязки
к именам GUID.
При старте backend загружает в память полные тексты страниц, прямо перечисленных в
`index.md`, вместе с заголовками, хлебными крошками, номерами строк и извлечёнными
ключевыми словами API. `search_indexed_pages` ищет по этому кэшу и возвращает только
релевантные выдержки; они помогают найти нужный раздел, но не заменяют чтение
документации при проверке деталей API.

Для `TFlexDOCs API/index.md` агент читает только первые 106 строк с оглавлением;
следующие строки с перечнем пространств имён используются только через точечный поиск.
В одном запросе агент ограничен 16 уникальными вызовами документационных инструментов;
повторный поиск или чтение того же фрагмента не возвращает содержимое повторно.
`search_docs` использует BM25 для ранжирования совпавших файлов по исходному вопросу
(с нормализацией частых русских окончаний); если исходный вопрос недоступен, сохраняется
обычная выдача ripgrep.
При `read_file(path)` без номера строки длинный документ начинается с заголовка,
наиболее релевантного исходному вопросу; выдача `list_dir` и `search_docs` оставляет
часть бюджета контекста для чтения найденного документа.

### Безопасность

- Документация монтируется в контейнер **read-only**: `./docs:/app/docs:ro`.
- Bash агенту недоступен: ни shell-инструмента, ни исполнения команд в сервисе нет.
  Единственный subprocess — `rg` (запускается `create_subprocess_exec`, не shell).
- Все пути в инструментах резолвятся и джейлится к `/app/docs`
  (`backend/app/doc_tools.py::safe_resolve`); symlinks учитываются.
  Абсолютные пути хоста сопоставляются с каталогом продукта внутри корня
  документации; итоговый путь всё равно проверяется на принадлежность `/app/docs`.
- Контейнер работает от непривилегированного пользователя; запись возможна только
  в `/app/data` (SQLite).

### Навыки исследователя

Методика исследователя адаптирована из `tflex-macro-api-research`,
`tflex-api-verification`, `tflex-safe-minimal-code` и предметных skills для объектов,
параметров, связей, жизненного цикла, стадий/подписей и ServerConnection. При запуске
приложению не нужна исходная папка с этими skills: их методики встроены в исследовательский
процесс. Дополнительно Pydantic AI Harness загружает по запросу навыки из
`backend/app/skills/`: навигационные карты объектных моделей T-FLEX CAD и T-FLEX DOCs,
CAD-сценарии написания кода для документа, 2D и 3D, а также сценарии импорта файлов,
редактирования объектов справочника и разработки DOCs-макросов. Навык параметров
описывает индексаторы `ParameterContainer`, проверку наличия и перечисление параметров,
навык стадий и подписей — `ObjectStages`, `Signatures`,
`ServerConnection.Stages`/`SignatureTypes` и смену стадии; их сигнатуры и примеры
вызовов сверены со справкой T-FLEX DOCs 17.6 и снабжены ссылками на
страницы-подтверждения. Навык макроязыка включает таблицу команд упрощённых макросов,
также сверенную со справкой, а карта объектной модели DOCs — файл связей
диаграммы Open API с методами на каждом ребре графа. Навыки импорта, генерации
тестовых данных, единиц измерения, плагинов/UI, редактирования объектов и ЭСИ
дополнительно содержат рабочие последовательности вызовов из каталога «Примеры
использования API» с точными ссылками файл:строка для `read_api_example`.
Отдельные навыки
покрывают справочник «Электронная структура изделий» (ЭСИ): вместе с навыком
поставляются таблицы GUID'ов типов и полей ЭСИ, по которым берутся точные
идентификаторы вместо угадывания. Навык отладки описывает LogWriter, классы
исключений макросов и типовые причины сбоев, словарь ошибок — категории отказов
сервера (`AccessDenied`, `ObjectNotFound`, `DatabaseError`, `SessionExpired`) и
стратегии их обработки. Навыки доступны исследователям и писателю кода; они помогают
выбрать направление работы, но не считаются спецификацией: сигнатуры и факты
проверяются в документации из `./docs`.

Помимо профильных DOCs-субагентов для импорта, тестовых данных, единиц и плагинов/UI
исследователь может делегировать задачи субагентам по бизнес-процессам (задания,
поручения, переменные процессов), по событиям (изменение параметров и связей,
завершение редактирования, события сервера), по отчётам и экспорту (генерация отчётов,
DataExchange, экспорт grb) и по стадиям и подписям объектов.

## Многопользовательский режим (вход по домену)

Приложение умеет работать как командный инструмент: каждый инженер входит под
своим доменным логином **без пароля** — Kerberos SSO (SPNEGO). Браузер на
доменной машине сам доказывает серверу личность пользователя; отдельной формы
входа нет. Пользователь заводится в БД автоматически при первом входе
(логин из билета, например `IVANOV@CORP.LOCAL` → `ivanov`).

- **Личные чаты**: каждый видит и ведёт только свою историю переписки.
  Обращение к чужому чату по прямому адресу API возвращает 404 — факт
  существования чужих чатов не раскрывается.
- **Администраторы** — список доменных логинов в `.env` (`ADMIN_USERS`,
  через запятую). Только админы видят шестерёнку настроек модели и страницу
  `/admin`, меняют глобальные настройки. Права применяются после правки
  `.env` и перезапуска — ничего в БД хранить не нужно.
- **Наследие**: чаты, созданные до включения многопользовательского режима
  (`user_id IS NULL`), отходят администраторам — обычным пользователям они
  не видны.
- **Аварийный вход**: `ADMIN_PASSWORD` (парольная форма `/admin`) остаётся
  запасным способом войти администратором при проблемах с доменом. Задавать
  его рекомендуется даже при рабочем SSO.
- **Обычный пользователь** видит: свой список чатов, чат-интерфейс,
  индикаторы состояния; настройки модели, ссылку «Администрирование агента»
  и чужие чаты — нет.
- Сессия — подписанная HttpOnly cookie на 12 часов; перевход происходит
  молча, при следующем открытии страницы.

Режим задаётся переменной `AUTH_MODE` в `.env`:

| Значение    | Поведение |
|-------------|-----------|
| `auto`      | по умолчанию: `kerberos`, если keytab доступен, иначе `off` (дев-машина без домена) |
| `kerberos`  | прод: если keytab недоступен — отказ запуска (fail-fast), а не тихое отключение входа |
| `off`       | без входа: псевдопользователь `dev` с правами админа (локальная разработка, тесты) |

## Запуск

```bash
docker compose up --build
```

- Фронтенд: <http://localhost:8080>
- API бэкенда: <http://localhost:8001/api/health>
- Документация API: <http://localhost:8080/docs> (ReDoc: `/redoc`) — открывать через
  порт фронтенда: статика Swagger UI/ReDoc локальная (`frontend/public/static/docs-assets`),
  интернет не нужен; на порту бэкенда страница будет без статики

Проверка доступности модели выполняет тестовый запрос к провайдеру; результат кешируется на
1 час, чтобы индикатор в браузере не расходовал квоту при каждом обновлении.

Провайдер, модель, API-адрес и ключ можно настроить через значок шестерёнки
в интерфейсе. Поддерживаются OpenAI, OpenRouter, Ollama, LM Studio и пользовательские
OpenAI-совместимые API. Настройки общие для всего сервера и сохраняются в SQLite;
API-ключ не возвращается браузеру, но хранится на диске без шифрования.
Используйте приложение только в доверенной сети: по умолчанию (`AUTH_MODE=auto`
без keytab, режим `off`) авторизации в API нет; доменный вход включается
развертыванием из раздела «Развёртывание Kerberos SSO» ниже.
При первом запуске начальные значения берутся из переменных окружения; после
сохранения в интерфейсе источником настроек становится база данных.
Поле «Модель» предлагает список моделей, которые провайдер отдаёт по API-адресу
(`GET …/models`). Список загружается при открытии настроек, после смены провайдера,
адреса или ключа и по кнопке «Обновить список»; при вводе названия он ищется по
подстроке. Для запроса списка сохранённый ключ используется, только если провайдер
и адрес совпадают с сохранёнными. Если провайдер не отдаёт список, название модели
вводится вручную.
В настройках задаётся размер окна контекста модели (4096–2 000 000 токенов):
это общий ориентир для запроса, истории чата и результатов поиска. Агент
резервирует до 20% окна для ответа, но не более 4096 токенов для исследователя
и писателя и 2048 для критика; при необходимости сокращает старую историю или
входной текст. Эти значения можно переопределить через `MAX_AGENT_RESPONSE_TOKENS`
и `MAX_CRITIC_RESPONSE_TOKENS`, чтобы не упираться в слишком жёсткий лимит модели.
Размер токенов оценивается консервативно (около 2 символов на токен), поскольку
для произвольных OpenAI-совместимых моделей точный токенизатор автоматически
не определяется. Для локальных моделей задайте окно по документации модели;
слишком большое значение может привести к ошибкам со стороны провайдера.

### Совместимость с локальными моделями

pydantic-ai формирует несколько system-сообщений (инструкции агента, подсказка
о подагентах, контекст отложенных возможностей). Строгие chat-шаблоны — Qwen 3.x
(`System message must be at the beginning`), часть Llama — на таком запросе
отвечают HTTP 500. Поэтому перед отправкой все system- и developer-сообщения
склеиваются в одно ведущее system-сообщение, порядок остальных сообщений не
меняется (`backend/app/llm_messages.py`). Проверка:
`python -X utf8 tests/test_system_message_merge.py`.

Настройте модель в `.env` (копия примера — `.env.example`):

```ini
AI_MODEL=openai:gpt-4o-mini
OPENAI_API_KEY=sk-...
# Полный лог ошибок LLM (трейсбек + последний запрос к модели):
LLM_ERROR_LOG_PATH=./data/llm-errors.log
# Повторы временных ошибок провайдера (502/503/504 и т.п.):
OPENAI_MAX_RETRIES=5
# Максимум запросов к модели за один запуск агента (по умолчанию 100):
AGENT_REQUEST_LIMIT=100
# При исчерпании квоты openrouter/free выберите другую доступную модель
# или пополните баланс OpenRouter.
# Порт бэкенда на хосте (если занят — выберите свободный):
BACKEND_PORT=8001
# локальный OpenAI-совместимый сервер (Ollama/vLLM и т.п.):
# OPENAI_BASE_URL=http://host.docker.internal:11434/v1
```

## Развёртывание Kerberos SSO

Подготовка на стороне домена (однократно, с администратором домена):

1. **SPN и DNS**: приложение открывается по имени `http://docs.corp:8080` —
   SPN `HTTP/docs.corp@CORP.LOCAL` выписан на сервисную учётную запись,
   DNS-запись `docs.corp` резолвится на сервер приложения с рабочих станций.
   По IP Kerberos не работает — только по этому имени.
2. **Keytab** от контроллера домена положить в `./secrets/docs-ai.keytab`
   (монтируется read-only через `docker-compose.prod.yml`).
3. **krb5.conf**: скопировать `deploy/krb5.conf.example` в `deploy/krb5.conf`
   и указать реальный realm и адреса KDC (контроллеры домена, порт 88 TCP).
4. В `.env` задать `AUTH_MODE=kerberos`, `ADMIN_USERS=ivanov,petrov`,
   `KRB5_PRINCIPAL=HTTP/docs.corp@CORP.LOCAL` (и аварийный `ADMIN_PASSWORD`).

Запуск на сервере:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

Базовый `docker compose up` (без prod-override и keytab) остаётся рабочим
для дев-машины — режим `auto` молча переключается в `off`. На проду
`AUTH_MODE=kerberos` обязателен: опечатка в пути keytab превращается в
отказ запуска, а не в открытое приложение.

Браузеры рабочих станций:

- **Edge/Chrome** на доменных машинах: имя `docs.corp` должно попадать в зону
  «Местная интрасеть» (GPO; имена с точками по умолчанию считаются
  Интернетом — проверьте, что GPO покрывает `docs.corp`).
- **Firefox**: `about:config` → `network.negotiate-auth.trusted-uris` =
  `docs.corp`.

### Чеклист первой проверки на месте

1. `docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend python -m app.auth --check`
   — печатает режим, читаемость keytab, principal, realm/KDC из krb5.conf,
   связность с KDC и готовность акцептор-учётных данных; код возврата 1 —
   там же напечатано, какой этап не прошёл.
2. Открыть `http://docs.corp:8080` в Edge на доменной машине: сплэш
   «Входим через домен…» сменяется интерфейсом, в сайдбаре — бейдж логина.
3. Типовые отказы:
   - **401 без заголовка `WWW-Authenticate`** в ответе на whoami — keytab/SPN
     (не совпадает principal, билет не принимается): смотреть лог бэкенда.
   - **Экран «Не удалось войти через домен»** — браузер не отдал токен: зона
     «Местная интрасеть»/Firefox не настроены, машина вне домена.
   - Панель диагностики на экране ошибки подсказывает те же шаги.

## Разработка без Docker (локально)

```bash
pip install -r backend/requirements.txt
# Windows/Linux нужен ripgrep в PATH
DOCS_ROOT=./docs OPENAI_API_KEY=sk-... python backend/run_server.py
```

Во втором терминале запустите фронтенд:

```bash
cd frontend
npm install
npm run dev
```

Откройте <http://localhost:5173>. Vite проксирует запросы `/api` на локальный backend.

## E2E-тесты (без реального LLM)

Мок OpenAI-API проверяет весь цикл: вызов инструмента -> критика -> финальный ответ.

```bash
python -X utf8 tests/test_e2e_mock.py     # пайплайн агентов
python -X utf8 tests/test_runs.py         # фоновые запуски: 202, догоняющий SSE, отмена
python -X utf8 tests/test_http_sse.py     # FastAPI + SSE + SQLite
python -X utf8 tests/test_llm_error_e2e.py     # полный дамп ошибки LLM в лог-файл
python -X utf8 tests/test_model_list.py   # список моделей провайдера: маршрут и правило ключа
node --test tests/frontend/model_filter.ts     # фильтр и лимит списка моделей
```
