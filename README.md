# Docs AI Agent

ИИ-агент-помощник, который читает и ищет информацию в тысячах файлов API-справки
и пишет рабочий код по найденной документации.

Состоит из фронтенда (React + TypeScript + Tailwind CSS) и бэкенда (Python 3.14 + pydantic-ai + FastAPI + SQLite),
запускается в Docker-контейнерах.

## Архитектура

```
[frontend nginx :8080] --proxy /api--> [backend uvicorn :8000]
                                          tools: ripgrep / read_file / file_info / list_dir
                                          agents: researcher -> DOCs/CAD specialists -> critic -> writer
                                          sqlite: чаты и история переписки
         ./docs (RO-маунт) ----------------------^
```

### Агентский цикл с критикой результата поиска

Каждое сообщение пользователя запускает пайплайн из трёх агентов:

1. **Researcher** — сначала определяет, относится ли вопрос к T-FLEX CAD или T-FLEX DOCs,
   затем ищет только в соответствующем подкаталоге корпуса инструментами (`search_docs`
   на ripgrep, `read_file`, `file_info`, `list_dir`) и выдаёт черновик фактов со ссылками
   `файл:строка`. Для предметного исследования он может делегировать задачу профильному
   субагенту T-FLEX DOCs или одному из CAD-субагентов (документ, 2D, 3D); результат
   возвращается исследователю для проверки.
   Для T-FLEX DOCs исследователь выбирает направление по сценарию
   (объекты, параметры, связи, жизненный цикл, UI и т. п.) и проверяет точные сигнатуры
   и порядок изменения объектов. Последующий ход идёт с накопленной историей.
2. **Critic** — структурированно оценивает, достаточно ли собранного для написания
   **рабочего** кода (подтверждённые сигнатуры, полнота сценария работы с API).
   Если нет — перечисляет конкретные пробелы и предлагает уточняющие ripgrep-запросы,
   и Researcher продолжает цикл (до `MAX_CRITIC_ROUNDS` итераций).
3. **Writer** — пишет финальный ответ с кодом C# по подтверждённым фактам и списком
   источников. Только подтверждённое документацией может попасть в код.

Все фазы стримятся во фронтенд по SSE (`phase`, `tool`, `draft`, `critique`, `text`).

### Инструменты агента

| Инструмент    | Что делает                                                                                                        |
|---------------|-------------------------------------------------------------------------------------------------------------------|
| `search_doc_topics` | Ищет GUID- и человекочитаемые страницы по иерархии `index.md` и возвращает доменный путь в оглавлении |
| `search_doc_intros` | Ищет по первым абзацам всех страниц, прямо указанных в `index.md`, и возвращает релевантные выдержки с путями |
| `search_docs` | Поиск кандидатов через **ripgrep** (regex или literal), затем ранжирование документов BM25 по исходному вопросу; `glob` ограничивает продукт |
| `read_file`   | Полное чтение файла (при переполнении бюджета контекста — порцией с подсказкой продолжения через `start_line`)      |
| `file_info`   | Оценка объёма файла: байты, строки, примерные токены, доля от окна контекста — чтобы не вылезти за контекст         |
| `list_dir`    | Листинг каталогов документации                                                                                     |

`search_doc_topics` использует иерархию ссылок из `index.md`, включая таблицу
пространств имён и таблицы типов на связанных страницах: сначала помогает выбрать
домен и страницу, затем `search_docs` и `read_file` подтверждают API по содержимому.
Это даёт будущим доменным навыкам и субагентам общий каталог вместо ручной привязки
к именам GUID.
Если название страницы в оглавлении слишком общее, `search_doc_intros` ищет по
первому абзацу каждой прямо указанной в `index.md` страницы. Это помогает найти
сценарии и примеры, упомянутые в вводном тексте; выдержки служат навигацией, а не
заменяют чтение полного документа.

Для `TFlexDOCs API/index.md` агент читает только первые 106 строк с оглавлением;
следующие строки с перечнем пространств имён используются только через точечный поиск.
В одном запросе агент ограничен 16 уникальными вызовами документационных инструментов;
повторный поиск или чтение того же фрагмента не возвращает содержимое повторно.
`search_docs` использует BM25 для ранжирования совпавших файлов по исходному вопросу
(с нормализацией частых русских окончаний); если исходный вопрос недоступен, сохраняется
обычная выдача ripgrep.
При `read_file(path)` без номера строки длинный документ начинается с заголовка,
наиболее релевантного исходному вопросу; выдача `list_dir` и `search_docs` оставляет
часть бюджета контекста для чтения найденного документа.

### Безопасность

- Документация монтируется в контейнер **read-only**: `./docs:/app/docs:ro`.
- Bash агенту недоступен: ни shell-инструмента, ни исполнения команд в сервисе нет.
  Единственный subprocess — `rg` (запускается `create_subprocess_exec`, не shell).
- Все пути в инструментах резолвятся и джейлится к `/app/docs`
  (`backend/app/doc_tools.py::safe_resolve`); symlinks учитываются.
  Абсолютные пути хоста сопоставляются с каталогом продукта внутри корня
  документации; итоговый путь всё равно проверяется на принадлежность `/app/docs`.
- Контейнер работает от непривилегированного пользователя; запись возможна только
  в `/app/data` (SQLite).

### Навыки исследователя

Методика исследователя адаптирована из `tflex-macro-api-research`,
`tflex-api-verification`, `tflex-safe-minimal-code` и предметных skills для объектов,
параметров, связей, жизненного цикла, стадий/подписей и ServerConnection. При запуске
приложению не нужна исходная папка с этими skills: их методики встроены в исследовательский
процесс. Дополнительно Pydantic AI Harness загружает по запросу навыки из
`backend/app/skills/`: навигационные карты объектных моделей T-FLEX CAD и T-FLEX DOCs,
CAD-сценарии написания кода для документа, 2D и 3D, а также сценарии импорта файлов,
редактирования объектов справочника и разработки DOCs-макросов. Навыки доступны
исследователям и писателю кода; они помогают выбрать направление работы, но не
считаются спецификацией: сигнатуры и факты проверяются в документации из `./docs`.

## Запуск

```bash
docker compose up --build
```

- Фронтенд: <http://localhost:8080>
- API бэкенда: <http://localhost:8001/api/health>

Проверка доступности модели выполняет тестовый запрос к провайдеру; результат кешируется на
1 час, чтобы индикатор в браузере не расходовал квоту при каждом обновлении.

Провайдер, модель, API-адрес и ключ можно настроить через значок шестерёнки
в интерфейсе. Поддерживаются OpenAI, OpenRouter, Ollama, LM Studio и пользовательские
OpenAI-совместимые API. Настройки общие для всего сервера и сохраняются в SQLite;
API-ключ не возвращается браузеру, но хранится на диске без шифрования.
Используйте приложение только в доверенной сети: авторизации в API нет.
При первом запуске начальные значения берутся из переменных окружения; после
сохранения в интерфейсе источником настроек становится база данных.
В настройках задаётся размер окна контекста модели (4096–2 000 000 токенов):
это общий ориентир для запроса, истории чата и результатов поиска. Агент
резервирует до 20% окна для ответа, но не более 4096 токенов для исследователя
и писателя и 2048 для критика; при необходимости сокращает старую историю или
входной текст. Эти значения можно переопределить через `MAX_AGENT_RESPONSE_TOKENS`
и `MAX_CRITIC_RESPONSE_TOKENS`, чтобы не упираться в слишком жёсткий лимит модели.
Размер токенов оценивается консервативно (около 2 символов на токен), поскольку
для произвольных OpenAI-совместимых моделей точный токенизатор автоматически
не определяется. Для локальных моделей задайте окно по документации модели;
слишком большое значение может привести к ошибкам со стороны провайдера.

Настройте модель в `.env` (копия примера — `.env.example`):

```ini
AI_MODEL=openai:gpt-4o-mini
OPENAI_API_KEY=sk-...
# Повторы временных ошибок провайдера (502/503/504 и т.п.):
OPENAI_MAX_RETRIES=5
# Максимум запросов к модели за один запуск агента (по умолчанию 100):
AGENT_REQUEST_LIMIT=100
# При исчерпании квоты openrouter/free выберите другую доступную модель
# или пополните баланс OpenRouter.
# Порт бэкенда на хосте (если занят — выберите свободный):
BACKEND_PORT=8001
# локальный OpenAI-совместимый сервер (Ollama/vLLM и т.п.):
# OPENAI_BASE_URL=http://host.docker.internal:11434/v1
```

## Разработка без Docker (локально)

```bash
pip install -r backend/requirements.txt
# Windows/Linux нужен ripgrep в PATH
DOCS_ROOT=./docs OPENAI_API_KEY=sk-... python backend/run_server.py
```

Во втором терминале запустите фронтенд:

```bash
cd frontend
npm install
npm run dev
```

Откройте <http://localhost:5173>. Vite проксирует запросы `/api` на локальный backend.

## E2E-тесты (без реального LLM)

Мок OpenAI-API проверяет весь цикл: вызов инструмента -> критика -> финальный ответ.

```bash
python -X utf8 tests/test_e2e_mock.py     # пайплайн агентов
python -X utf8 tests/test_http_sse.py     # FastAPI + SSE + SQLite
```

## Структура

```
backend/app/config.py   конфигурация (env)
backend/app/doc_tools.py инструменты файловой системы + ripgrep
backend/app/agent.py    агентский цикл: researcher / critic / writer
backend/app/db.py       SQLite (чаты, сообщения, история pydantic-ai)
backend/app/main.py     FastAPI + SSE
frontend/src/            React + TypeScript чат, стили Tailwind CSS
frontend/                Vite-сборка для nginx и локальная разработка
tests/                  мок-LLM и e2e-тесты
```
