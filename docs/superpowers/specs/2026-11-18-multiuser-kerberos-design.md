# Многопользовательский режим: вход по домену (Kerberos SSO)

Дата: 2026-11-18
Статус: на утверждении

## Зачем

Сейчас в приложении нет понятия пользователя: все чаты общие и доступны
любому, кто открыл страницу. Приложение переезжает из «инструмента одного
человека» в командное использование: несколько инженеров одновременно,
каждый со своей историей переписки.

Вход — без единого пароля: Kerberos SSO против домена Active Directory.
Пользователь открывает приложение — браузер сам доказывает серверу его
доменную личность. Keytab от контроллера домена уже имеется.

## Цели

- Каждый пользователь видит и ведёт только свои чаты.
- Вход прозрачный: доменный логин, никаких форм и паролей.
- Пользователи заводятся сами при первом входе (логин из билета).
- Права администратора — по списку логинов в `.env` (`ADMIN_USERS`).
- Настройки модели и конфигурация агента — глобальные, менять могут
  только администраторы.
- Работа в изолированной ЛВС без интернета: все новые зависимости
  вендорятся в репозиторий по уже отработанным схемам (`.deb` в
  `backend/packages/`, wheels в `backend/wheels/`).

## Не-цели

- Персональные настройки модели (провайдер/лимиты) — остаются общими.
- Квоты и лимиты запросов на пользователя.
- Отображаемые имена (ФИО из AD) — показываем короткий логин; подтянуть
  ФИО из LDAP можно позже отдельной задачей.
- Группы AD как источник прав админа — только явный список логинов.
- HTTPS-терминация — остаётся как сейчас (HTTP в изолированной ЛВС).
- Управление пользователями в UI — пользователи создаются сами, ручное
  управление не нужно (удаление пользователя = очистка строки в БД).

## Анти-цели

- Парольный вход для обычных пользователей — недопустим по решению
  заказчика («без паролей»). Пароль остаётся только как аварийный вход
  администратора при проблемах с доменом.
- Доступ к чужим чатам или глобальным настройкам без прав — даже по
  прямой адресации API (`/api/chats/{id}` чужого владельца → 404).

## Ограничения

- Развёртывание офлайн: образы собираются без сети, только из
  вендоренных артефактов.
- `python-gssapi` — C-extension, готовых manylinux-колёс на PyPI нет;
  собирается из исходников с заголовками MIT Kerberos. Решение: колесо
  собирается один раз на машине с интернетом в том же базовом образе
  (`python:3.14-slim`) и кладётся в `backend/wheels/`.
- Разработка и тесты идут на Windows без Kerberos: импорт gssapi только
  ленивый, внутри kerberos-режима; тесты мокают SPNEGO-слой.
- Kerberos требует постоянного имени приложения, по IP не работает. SPN
  выписан: `HTTP/docs.corp@CORP.LOCAL` — приложение открывается по
  `http://docs.corp:8080` (DNS-запись `docs.corp` → сервер).

## Варианты

1. **Kerberos в бэкенде (Python)** — выбран. Frontend-nginx не меняется;
   pyspnego + python-gssapi в бэкенд-образе, keytab/krb5.conf монтируются
   в бэкенд. Вся аутентификация в одном месте, в тестируемом коде.
2. Apache + mod_auth_gssapi вместо nginx на фронте — без компиляции, но
   переписывание рабочего nginx-фронта на конфигурацию Apache и размытие
   аутентификации между контейнерами. Отклонён.
3. Кастомная сборка nginx со SPNEGO-модулем — компиляция из вендоренных
   исходников, самый хрупкий вариант. Отклонён.

## Дизайн

### Режимы аутентификации

`AUTH_MODE` (env, по умолчанию `auto`):

- `auto` — дев: если задан `KRB5_KEYTAB` и файл существует —
  `kerberos`, иначе `off`.
- `kerberos` — прод: если keytab недоступен/нечитаем — отказ запуска
  (fail-fast), а не тихое отключение аутентификации. Опечатка в пути
  keytab не должна превращаться в открытый приложение.
- `off` — явное отключение (локальная разработка, тесты): все маршруты
  ведут себя как сейчас, действует псевдопользователь `dev` (админ);
  при старте пишется громкое предупреждение в лог.

Существующие тесты и локальная разработка на Windows не ломаются.

### Вход (SPNEGO)

Новый маршрут `GET /api/auth/whoami`:

1. Нет валидной cookie сессии → `401` + `WWW-Authenticate: Negotiate`.
   Браузер (fetch, same-origin) повторяет запрос с заголовком
   `Authorization: Negotiate <токен>` автоматически.
2. Бэкенд проверяет токен серверным контекстом pyspnego (акцептор,
   ключ из keytab по `KRB5_KTNAME`, principal — из `KRB5_PRINCIPAL`;
   если не задан — первый HTTP-principal из keytab). Ожидается
   одноэтапный обмен (норма для AD); если контекст запросил
   продолжение — `401` с предложением начать заново.
3. Логин из билета (`IVANOV@CORP.LOCAL` → `ivanov`): пользователь
   создаётся в БД при первом входе, обновляется `last_seen_at`.
4. Выдаётся HttpOnly cookie `docs_ai_session` — HMAC-SHA256 подпись
   (`user-session-v1:{login}:{expires}`), срок 12 ч, `samesite=strict`,
   `path=/api`. Формат и механика — как у существующей админской cookie.
5. Ответ: `{login, is_admin}`.

`POST /api/auth/logout` — удаляет cookie (перевход произойдёт молча при
следующем `whoami`). Кнопки в UI не будет.

Ключ подписи сессий: генерируется `secrets.token_hex(32)` при первом
старте и хранится в таблице `app_meta` в SQLite-томе — переживает
рестарты, не требует нового секрета в `.env`.

Ошибка Negotiate (домен недоступен, браузер не отдал токен, Firefox без
настройки) → во фронтенде полноэкранный экран «Не удалось войти через
домен» с подсказками (настроить Firefox/зайти Edge/обратиться к админу),
без возможности пользоваться приложением анонимно.

### БД

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    login TEXT NOT NULL UNIQUE,        -- 'ivanov' (нижний регистр)
    upn TEXT NOT NULL,                 -- 'IVANOV@CORP.LOCAL'
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    last_seen_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE app_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
ALTER TABLE chats ADD COLUMN user_id INTEGER REFERENCES users(id);
```

- Существующие чаты получают `user_id = NULL` — «наследие»: видны и
  открываются только администраторам, обычным пользователям не видны.
- `is_admin` не хранится: вычисляется на каждом запросе из `ADMIN_USERS`
  (env — источник правды, правка без миграции БД).

### Права на маршрутах

| Маршрут | Кто |
|---|---|
| `/api/health`, `/api/health/model` | любой вошедший (healthcheck Docker ходит без cookie — остаётся открытым `/api/health`) |
| `/api/auth/*` | без аутентификации (сам вход) |
| `/api/chats`, `/api/chats/{id}/**` | владелец чата; наследие (`user_id NULL`) — админ |
| `PUT /api/settings` | только админ (сейчас открыт всем — закрытие существующей дыры); `GET` — любой вошедший |
| `/api/tools/search-indexed-pages` | любой вошедший |
| `/api/admin/**` | админ: SSO-сессия с логином из `ADMIN_USERS` **или** прежняя парольная cookie (`ADMIN_PASSWORD`, ≥16 символов, rate-limit сохраняются) |
| `/docs`, `/redoc`, `/openapi.json` | без изменений (локальная справка API) |

`require_user` / `require_admin` — FastAPI-зависимости в новом модуле
`backend/app/auth.py`. Проверка владения чатом — внутри обработчиков
чатов (404 вместо 403, чтобы не раскрывать существование чужих чатов).

CSRF: мутирующие `/api/admin/**` по-прежнему требуют заголовок
`X-Admin-Request: 1`; для мутирующих пользовательских маршрутов
достаточно `samesite=strict` cookie.

### Фронтенд

- При загрузке: `GET /api/auth/whoami`. Пока идёт Negotiate — сплэш
  «Входим через домен…»; 401 после попытки — экран ошибки с подсказками.
- В сайдбаре — бейдж с логином вошедшего.
- Ссылка «Администрирование агента» и шестерёнка настроек модели —
  только для `is_admin`.
- `AdminPage.tsx`: при заходе сначала пробует существующую админ-сессию
  через SSO-cookie; если логин в `ADMIN_USERS` — пускает без парольной
  формы. Парольная форма остаётся запасным входом.

### Вендоринг и сборка

- `backend/wheels/`: `pyspnego` + зависимости (чистый Python) и колесо
  `gssapi`, собранное вручную (документируемая one-off процедура:
  временный `Dockerfile --target=wheel-builder` на машине с интернетом
  из того же `python:3.14-slim` + `libkrb5-dev`, колесо кладётся в
  `backend/wheels/`). Требование: базовый образ не меняется без
  пересборки колеса.
- `backend/packages/`: runtime-библиотеки krb5 (libgssapi-krb5-2,
  libkrb5-3, libk5crypto3, libcom-err2 и зависимости) — `.deb` из
  Debian trixie amd64, установка через `dpkg -i` как у ripgrep.
- `docker-compose.yml` (базовый): проброс env (`KRB5_KTNAME`,
  `KRB5_PRINCIPAL`, `ADMIN_USERS`, `AUTH_MODE`); порт бэкенда
  `127.0.0.1:8001:8000` — мимо nginx аутентификацию не обойти (дебаг —
  по SSH-туннелю). Базовый compose остаётся рабочим для дев-машины без
  keytab.
- `docker-compose.prod.yml` (override для прода): монтирование
  `./deploy/krb5.conf:ro` и `./secrets/docs-ai.keytab:ro`. Запуск на
  сервере: `docker compose -f docker-compose.yml -f
  docker-compose.prod.yml up`. Отсутствующие файлы не ломают
  локальный `docker compose up`.

### Развёртывание (новый раздел README)

- SPN/keytab: приложение открывается по `http://docs.corp:8080` (SPN
  `HTTP/docs.corp@CORP.LOCAL`); DNS-запись `docs.corp` должна
  резолвиться на рабочих станциях; контейнер видит KDC (krb5.conf).
- Браузеры: Edge/Chrome на доменных машинах — автоматически при
  попадании имени `docs.corp` в зону «Местная интрасеть» (GPO; имена с
  точками по умолчанию считаются Интернетом — проверить). Firefox:
  `network.negotiate-auth.trusted-uris = docs.corp`.
- `.env.example`: `ADMIN_USERS`, `KRB5_KTNAME`,
  `KRB5_PRINCIPAL=HTTP/docs.corp@CORP.LOCAL` — SPN задаётся в `.env`,
  не в коде; при смене keytab правится только `.env`.

### Тесты (check-функции, без pytest)

Новый `tests/test_auth.py`: подпись/проверка cookie (включая подделку и
просрочку); `require_user`/`require_admin` в обоих режимах; SPNEGO-ручка
с замоканным акцептором (успех → cookie + автосоздание пользователя,
мусорный токен → 401). `tests/test_chats_multuser.py`: изоляция чатов
двух пользователей, наследие видно только админу, чужой чат → 404,
`PUT /api/settings` не-админом → 403, миграция существующей БД
(появление `user_id`, NULL сохранён). Существующие e2e-тесты гоняются в
`AUTH_MODE=off` без изменений.

## Мои решения (принимались без заказчика — проверить)

1. Срок сессии — 12 ч (перевход происходит молча, боль незаметна).
2. Ключ подписи сессий — авто-генерация в `app_meta`, а не env-секрет.
3. `/docs`/`/redoc` остаются открытыми — локальная справка, вреда нет.
4. `GET /api/settings` доступен любому вошедшему (там нет ключа,
  только флаг `api_key_configured`).
5. Наследие-чаты (`user_id NULL`) видны только админам; отдельной
   передачи владельцу не делаем.
6. Порт бэкенда на хосте привязываем к 127.0.0.1 — подтверждено
   заказчиком (напрямую на бэкенд не заходят).
7. Firefox требует ручной настройки — считаем допустимым, основных
   браузеров достаточно (Edge/Chrome).
8. `ADMIN_PASSWORD` — опционален: SSO-админ работает и без него;
   при незаданном пароле отключена только парольная форма входа (сейчас
   при незаданном пароле весь админ-API отвечал 503 — перестраиваем).
   README рекомендует задавать его как аварийный вход.
9. Автоповтор fetch с Negotiate-токеном (same-origin 401 → повтор с
   `Authorization`) — штатное поведение Edge/Chrome/Firefox; ложится в
   дизайн как проверенный факт, финальная сверка — на реальной доменной
   машине при подготовке развёртывания.
10. Монтирования keytab/krb5.conf — только в `docker-compose.prod.yml`
    (override); базовый compose остаётся рабочим на дев-машине.
11. `AUTH_MODE` пиннуется явно для прода (`kerberos`, fail-fast при
    недоступном keytab); по умолчанию `auto` — тихий офлайн-режим не
    может случиться на проде по опечатке.
12. Команда самопроверки в контейнере (`python -m app.auth --check`):
    печатает режим, читаемость keytab, найденный principal,
    резолвинг KDC из krb5.conf и связность с ним. Так как первая
    проверка реального входа — на месте в ЛВС, отлаживать «не входит»
    придётся в поле: команда должна локализовать этап отказа без
    интернета и сторонних инструментов.
13. Подробные логи старта Kerberos-пути (загружен keytab, principal,
    режим) и содержательные ответы об ошибках Negotiate (в лог, не
    клиенту); README-чеклист развёртывания с пошаговой проверкой входа
    и типовыми причинами отказа.

## Решения заказчика

- SPN keytab: `HTTP/docs.corp@CORP.LOCAL`; приложение открывается по
  `http://docs.corp:8080`. Имя `docs.corp` должно попадать в зону
  «Местная интрасеть» на рабочих станциях (см. раздел развёртывания).
- Публикацию порта бэкенда ограничить `127.0.0.1` (п.6).
- SPN задаётся в `.env` (`KRB5_PRINCIPAL`), не в коде.
- Первая проверка реального Kerberos-входа — на месте в ЛВС, при
  развёртывании. До этого путь «билет → keytab → логин» проверяется
  только моками. Поэтому план обязателен к пунктам 12–13 ниже.
